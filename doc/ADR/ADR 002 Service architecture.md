# ADR 002 Service Architecture

## Статус

Разрабатывается

## Контекст

Необходимо зафиксировать подходы к архитектуре сервиса, что включает:

1. Слои и их зависимости

2. Шаблоны используемые в разработк

3. Структуру сборок в проекте сервиса и из зависимости

## Решение

При создании сервисов должна использоваться чистая архитектура в которой слои должны зависеть по возможности от абстракций (интерфейсов), а не конкретных классов. Для моделирования предметной области испльзуется подход DDD (Domain Driven Design).

Сервис состоит из трех основных слоев:

1. Доменый слой. Содержит классы, описывающие модель предметной области.

2. Прикладной слой. Содерит сервисы, реализующие сценарии использования доменных объектов. Также содерит интерфейсы, доступа к данным.

3. Инфраструктурный слой. Содержит реализацию репозиториев и клиентов других севрисов.

Проект сервиса включает по отдельной сборке для каждого слоя.

1. Инфраструктурная сборка. Содержит точку входа приложения и все классы инфраструктурного слоя. Сборка называется как основной агрегат плюс постфикс Service, например PersonService. Инфраструктурная сборка зависит от прикладной и доменной сборок

2. Прикладная сборка. Содержит все классы прикладного слоя и называется как инфраструктурная сборка плюс постфикс Application через точку, например PersonService.Application. Зависит только от доменной сборки

3. Доменная сборка. Содержи реализацию классов доменной области. Не зависит от других сборок в проекте

Каждый сервис распологается в своей отельной папке в корне репозитория.

## Последствия

Закрепление архитектуры сервиса позволит создавать хорошо структурированный код, которых легко поддерживать.
